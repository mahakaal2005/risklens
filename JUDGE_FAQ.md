# Judge FAQ — ClearRisk Recover

Anticipated questions, with the actual evidence and file/line so any answer here
can be pulled up live during a demo or panel review. This is a companion to
`README.md`, `MODEL_CARD.md`, `RISK_POLICY.md`, `DATA_DICTIONARY.md`, `PRD.md`,
and `SECURITY.md` — not a replacement for them.

---

**Q: Is the label circular — did you just define "high risk" as whatever the
rules engine flags, then call that a win?**

No. `label_high_loss_next_30d` is generated by a hidden 5-state latent-merchant
simulation (Stable, Seasonal/legitimate high-return, Operational fulfilment
failure, High-risk, Early hidden-risk) in `ml/generate_synthetic_data.py` — see
`DATA_DICTIONARY.md` for the exact state definitions. The rules engine
(`rules/`, `ml/rules_engine.py`) evaluates the same merchant-week aggregates
independently and never has access to the latent state. This is why the
dataset can deliberately include false-positive examples (a legitimate
seasonal-sale merchant with a temporarily high return rate) and false-negative
examples (an early hidden-risk merchant whose visible metrics haven't moved
yet) — those only exist because the label isn't a function of the rule
thresholds.

**Q: Why isn't precision/recall higher — a lot of hackathon ML demos show
95%+?**

Because a near-perfect score triggers an automatic investigation gate before
it can be used in the pitch, and this project documents running that gate
rather than skipping it. `MODEL_CARD.md:423-439` — the rule: PR-AUC ≥ 0.98, or
precision and recall both ≥ 0.98, or zero false positives/negatives on a
meaningful test set, means "mark Under investigation, do not headline it until
seven specific leakage/integrity checks pass." The gate was **not** triggered
for any of the five evaluated methods, including both tree-based comparison
baselines — the best PR-AUC achieved was 0.693 (Gradient Boosting)
(`MODEL_CARD.md:439`). All five methods are reported as APPROVED, meaning the
numbers in the README's comparison table (Logistic Regression PR-AUC 0.664,
Random Forest 0.689, Gradient Boosting 0.693, Trajectory Transformer 0.688,
rules-only 0.288) are the real, un-inflated held-out result — not a headline
number chased down to it.

**Q: Is the probability the model states actually trustworthy, or just
well-ranked?**

Both are measured separately, because they're different properties — a model
can rank correctly while stating a number that's wrong. Every model is
calibration-tested (`ml/calibration.py`: Brier score, expected calibration
error, maximum calibration error, reliability curve). This caught a real bug:
raw Random Forest states a mean predicted probability of **0.288 against a
true base rate of 0.145** — it overstates true risk by roughly 2x
(`MODEL_CARD.md:157,169`). That inflation is also the reason Random Forest's
selected operating threshold (0.55) looked anomalous next to every other
model's 0.10-0.15 — calibration analysis turned an unexplained oddity into a
measured, understood property instead of leaving it as a mystery. It was also
found that post-hoc calibration (Platt scaling) *worsens* the Trajectory
Transformer's worst-bin error (`MODEL_CARD.md:187`) — so "just apply isotonic
calibration to everything" is explicitly reported as the wrong fix where it's
wrong, not applied uniformly for a cleaner-looking table.

**Q: What does this actually cost in rupees, and does the ML add real value
over doing nothing clever?**

Every method is costed against two baselines — reviewing nobody (₹37.6M) and
reviewing everybody (₹22.4M) — using assumed but explicit rupee constants in
`rules/cost_model.yaml` and `ml/cost_model.py`. Two findings the accuracy table
alone hides:

- **The rules-only baseline does not beat reviewing everybody.** It costs
  ₹29.3M — *more* than the ₹22.4M trivial "review everything" policy
  (`MODEL_CARD.md:228`). A team running rules alone would be better off with
  no model at all.
- **The best ML method beats review-everything by only ~12%** (₹19.7M vs.
  ₹22.4M) (`MODEL_CARD.md:230`), because the assumed 72:1 miss-to-review cost
  ratio makes over-flagging nearly free — most of the value comes from
  reviewing a lot, not from the model's discrimination.

Every rupee figure is explicitly labeled an assumption, not a measured real
cost (`MODEL_CARD.md:199`) — a sensitivity table reports how the recommended
threshold moves across cost ratios from 10:1 to 500:1, so a reader can locate
their own ratio instead of inheriting ours.

**Q: What would it take to connect this to a real Razorpay integration?**

See the "Path to Production" section of `README.md`. Short version: the event
normalization/aggregation logic (`ml/razorpay_adapter.py`) is built to accept
real webhook events in place of local fixtures, but three things are
genuinely unbuilt, not just unconfigured — real webhook auth/signature
verification, a second data source for six merchant-week fields Razorpay
payment events cannot supply (merchant category/age, delivery-evidence
coverage, support-ticket metrics, prior review outcome), and a real-world
definition of the outcome label to replace the synthetic simulation before any
retraining could be trusted on live merchants.

---

**Q: Why one risk scenario instead of a broader fraud/risk platform?**

Deliberate scope decision, documented in `PRD.md`'s "Out of scope" section:
per-transaction fraud scenarios, account-takeover detection, and a
multi-scenario platform were explicitly moved to future work rather than
attempted in Phase 1. The stated reasoning (`PRD.md` section 11, "Risks and
mitigations"): scope creep back toward multiple loss classes was identified as
a named risk, and the mitigation was to limit Phase 1 to one flagship scenario
so it could be built and evaluated to the rigor shown above, rather than
spreading effort thin across several shallow scenarios.

**Q: Could this system actually take a real enforcement action — freeze funds,
ban a merchant, reject a payment?**

No, and this is enforced by an automated test, not just a design document. The
policy engine can only return one of five recommendation values (`APPROVE`,
`ALLOW_WITH_MONITORING`, `REQUEST_EVIDENCE`, `MANUAL_REVIEW_REQUIRED`,
`ESCALATE_TO_COMPLIANCE`) — see `PRD.md` FR-5. `tests/test_api_cases.py::
test_no_route_or_response_contains_prohibited_enforcement_words` scans the
live OpenAPI schema for `freeze`/`ban`/`terminate`/`hold settlement`/etc. and
fails the build if any endpoint or response could contain them. Separately,
`app/services/audit_service.py` refuses to persist any audit payload
containing those enforcement terms outright (`SECURITY.md`, "Sanitised audit
payloads") — the write is rejected, not silently stripped.
