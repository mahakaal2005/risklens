## 8. Defects fixed

### Defect 1: validator did not reject unexpected/unknown top-level or method-level fields

- **The defect:** `validate_report()` only checked for a *fixed list* of known-bad substrings (latent-state names, enforcement words, merchant-ID pattern). A report that was otherwise schema-complete but contained an arbitrary extra field — e.g. a debug field accidentally containing a fake stack trace or a credential-looking string — passed validation with zero issues.
- **How it was reproduced:** Loaded the real report, added `report['debug_internal'] = 'stack trace: /home/rudra/.../app/main.py line 42, password=hunter2'`, called `validate_report(report)` → returned `[]` (no issues) before the fix.
- **The exact fix:** Added two checks in `ml/evaluation_report.py::validate_report()`: (1) `unexpected_top_level = set(report.keys()) - REQUIRED_TOP_LEVEL_KEYS` — any non-empty result is now an issue; (2) the equivalent check per-method (`unexpected_keys = set(metrics.keys()) - REQUIRED_METHOD_METRIC_KEYS`). Confirmed the real, legitimately-built report still validates cleanly afterward (its `build_report()` output only ever contains the exact required keys).
- **The new test proving it:** `tests/test_evaluation_report.py::test_validate_report_rejects_unexpected_top_level_field` and `::test_validate_report_rejects_unexpected_method_field`.

### Defect 2: report writes were not atomic

- **The defect:** `save_report()` wrote directly to `ml/artifacts/latest_evaluation_report.json` via `open(path, "w")`. If the evaluation process were interrupted mid-write (crash, kill, disk full), a reader (`GET /metrics`) could observe a truncated/corrupt file — the malformed-JSON code path (Condition C) would still handle this safely, but the corruption itself was avoidably possible.
- **How it was reproduced:** Not reproduced as a runtime failure (would require deliberately killing the process mid-write); identified by direct code inspection per the review checklist's explicit prompt ("preferably temporary file + atomic rename if this can be added without scope creep").
- **The exact fix:** Added `_write_json_atomically()` in `ml/evaluation_report.py`, writing to a `.tmp<pid>` file in the same directory, flushing and `fsync`-ing, then `os.replace()`-ing into place (atomic on POSIX and Windows). `save_report()` now calls this helper for both the `latest_evaluation_report.json` and the timestamped copy.
- **The new test proving it:** No new dedicated test was added for this one (atomicity under mid-write interruption is difficult to test deterministically without fault injection); verified instead by re-running the full pipeline (`python3 -m ml.evaluate_model`) after the change and confirming the resulting file is valid JSON, passes `validate_report()`, and no `.tmp*` files are left behind. This is a documented gap: **the atomicity fix itself is not covered by an automated test**, only by manual confirmation.

No other defects were found and fixed. The `docs/API_CONTRACT.md` staleness (Section 7) was identified but intentionally **not** fixed, since that file was outside Milestone 7's authorized edit scope — flagged for your decision instead.
